## Восстановленные решения (из погибших чатов)

1. Вектор: улучшить ВСЁ — Visual UI/Mini App + Функции/логика + Стек. Цель = planner v2 уровня Ledger: чистый бэкенд + Mini App + лучше функции + умнее AI.
2. Пользователи: SINGLE-USER. Выкинуть ACL / shared / private / мультиюзер полностью (было 2 брата). Упрощает модель прав на порядок.
3. Модули v2 (полный личный life-OS): Inbox + AI-разбор; Задачи + календарь; Проекты + заметки; Привычки + цели.
4. Способ планирования (сердце планнера): пользователь планирует САМ, AI — копайлот. AI подсказывает что забыл, как лучше по времени, как продуктивнее. По запросу AI составляет план сам, пользователь корректирует. => не чистый Eisenhower-only и не авто-AI; гибрид, человек у руля, время/расписание важны.

5. Модель задач/планирования = КАК В TICKTICK. Значит фичсет:
   - Задачи: списки + папки + теги + 4 приоритета + подзадачи/чеклисты + заметка в задаче
   - Даты: due date + time, напоминания, повторяющиеся задачи (recurring)
   - Smart-списки: Inbox, Сегодня, Завтра, Следующие 7 дней, по тегам
   - Виды: список, календарь (день/неделя/месяц), матрица Эйзенхауэра (как отдельный вид), возможно kanban
   - Привычки: встроенный трекер привычек (streak) — закрывает модуль "Привычки"
   - => Eisenhower остаётся, но как ОДИН из видов, не единственная модель. Гибрид встроен.

6. Календарь: ВНУТРЕННИЙ календарь в Mini App. Google Calendar sync НЕ нужен (ни синк, ни read-only).
7. Цели (goals): ОТДЕЛЬНЫЙ модуль. Большая цель -> разбивается на задачи/привычки, прогресс в %. Связь goal -> tasks/habits.

8. Захват через бота:
   - Inbox-БУФЕР остаётся + ручной разбор (НЕ мгновенное авто-создание задачи). Бот = быстрый сброс в Inbox.
   - Типы: ТЕКСТ, ФОТО, ССЫЛКА. Голос УБИРАЕМ совсем (не пользуется) -> Whisper вон.
   - Файл/документ как тип захвата не нужен.
   - Фото/ссылка -> скорее ВЛОЖЕНИЯ к задаче (при разборе Inbox прикрепляются к задаче/заметке).

9. AI-копайлот:
   - Делает: (1) разбор Inbox -> предлагает поля задачи; (2) план дня/недели по запросу; (3) проактивные пинги.
   - Режим: ГЛАВНОЕ — по запросу ("когда я спросил"). Проактив — МЯГКИЙ, как советы в отдельном месте куда можно сослаться, без навязчивых уведомлений.
   - КЛЮЧЕВОЕ: разговорный LLM с ПОСТОЯННЫМ пониманием контекста. Пользователь общается с ботом естественно, бот знает всё состояние планнера (задачи/проекты/привычки/цели) и держит контекст диалога. Это главное отличие от v1 (там были команды + intent-роутер).
   - Следствие: нужен контекстный/память-слой для LLM поверх состояния планнера.

10. Хранение (решено мной, пользователь сказал "определи сам"):
    - Пользователь НИЧЕГО не пишет руками, Obsidian для правки не открывает.
    - => ВСЁ В POSTGRES. Mini App — единственная поверхность. Markdown/git/Obsidian УБИРАЕМ.
    - Причина: Obsidian-как-БД = лишний sync-слой и сложность без пользы при наличии Mini App; Postgres + типизированные API проще, без git-гонок и file I/O, удобнее для AI-инструментов.
    - Вложения (фото/ссылки): отдельное хранилище — диск VPS или Telegram file_id. Детали в дизайне.

11. UI/UX Mini App (Air-Bank style: чисто, карточки, мягкие цвета, нижние табы):
    - Вариант B: AI = FLOATING-кнопка на всех экранах (не отдельный таб).
    - Цели важнее привычек: ПРИВЫЧКИ вложены ВНУТРЬ Целей.
    - Inbox: вход внутри таба "Сегодня" с бейджем-счётчиком (отдельного таба нет, но Inbox нужен).
    - Итоговые 5 нижних табов:
      1. Сегодня (agenda дня: задачи + привычки + карточка совета AI + вход в Inbox с бейджем)
      2. Календарь (день/неделя/месяц, задачи на слоты времени)
      3. Задачи (списки/проекты, smart-списки 7дней/теги, вид-матрица Эйзенхауэра)
      4. Цели (цели с прогрессом %, привычки/streak вложены внутрь цели)
      5. Проекты / заметки
    - AI floating: чат-копайлот со знанием полного контекста, вызывается с любого экрана.

## Решения по стеку/архитектуре

12. Подход: A — ЧИСТЫЙ REBUILD по стеку Ledger. v1 = только референс.
    - Стек: FastAPI + Postgres + SQLAlchemy/Alembic + React/TS Mini App (Vite) + Caddy (HTTPS) + Docker + python-telegram-bot + LLM.
    - Переиспользуем каркас Ledger (структура src/, alembic, docker-compose, Caddyfile, frontend/).
    - Выкидываем из v1: NocoDB, git-markdown слой, мультиюзер/ACL, голос/Whisper, Эйзенхауэр-как-единственная-модель.
13. LLM-стратегия (поэтапно, под free-stack):
    - СТАРТ: бесплатная классификация (Groq/Gemini free) для разбора Inbox + парсинга.
    - Тестим качество диалога/копайлота.
    - Claude подключаем ПОЗЖЕ, если бесплатного качества не хватает для разговорного копайлота.
14. Mini App требует HTTPS-домен (Telegram). Схему Caddy+домен берём как в Ledger.
15. МОДУЛЬ Session Intake (захват рабочей сессии -> декомпозиция):
    - Назначение: итог рабочей сессии (задачи + план + способы реализации, например после работы с Claude Code) попадает в planner и AI разбирает его в задачи/план внутри нужного проекта.
    - Поток: итог сессии -> создаётся спец inbox_item (тип `session`) -> AI декомпозирует (задачи с приоритетом/датой, план как заметка проекта, способы реализации как подзадачи/notes, предлагает проект) -> пользователь разбирает из Inbox (подтверждение встроено) -> падает в planner.
    - Отдельного таба в Mini App НЕТ. Всё идёт через Inbox.
    - Проект: AI предлагает сам, пользователь подтверждает при разборе.
    - ИНТЕГРАЦИЯ: скилл `/wrapup` РАСШИРЯЕМ — помимо лога в NotebookLM «AI Brain» он шлёт структурный итог сессии в planner (ingest). => planner нужен аутентифицированный ingest-эндпоинт, который wrapup вызывает.
16. Inbox = ДЕФОЛТНЫЙ СБОРНИК ВСЕХ новых задач (TickTick-семантика):
    - Сюда падают и задачи что пользователь заносит сам (быстрый ввод), и задачи что AI напарсил (захват/сессии).
    - Задача без назначенного проекта/списка живёт в Inbox.
    - Из Inbox пользователь раскидывает по проектам/спискам.
    - РАЗДЕЛЕНИЕ ПО ИСТОЧНИКУ (кнопки/фильтры в Inbox), чтобы не путаться откуда задача:
      "Мои" (занёс сам) vs "Из сессий/проектов" (AI напарсил из wrapup/сессий). Поле task/inbox_item.source.
17. ЭКОСИСТЕМА (round-trip Claude Code <-> planner). Planner = ЦЕНТРАЛЬНЫЙ ХАБ задач:
    - Не только сессия -> planner (ingest), но и planner -> ОБРАТНО в проект.
    - Сценарий: начинаешь проект в Claude Code -> Claude должен видеть из planner какие задачи ты завершил, какие висят, какой план -> продолжает осмысленно.
    - Нужен read/write API planner + проектная сторона (скилл в Claude Code), связка репозиторий <-> planner project.
    - Пользователь работает в нескольких проектах (ZIMA, Ctok, MR-VLAD, Champ, ...) -> planner ведёт задачи всех.
    - РЕШЕНО:
      - Inbox-фильтры: "Мои" / "Из сессий".
      - Claude Code сторона ТОЛЬКО ЧИТАЕТ контекст из planner (read-only). Done пользователь отмечает сам в planner. Безопаснее (Claude не ошибётся со статусами).
      - Mapping репо -> planner project хранится НА СТОРОНЕ PLANNER (таблица repo_link: repo_key=имя папки/git-remote -> project_id). Скилл /planner определяет репо, спрашивает planner. Первая привязка -> planner запомнил. БЕЗ файла в репо, БЕЗ постоянных коммитов (важно для пользователя — он не хочет коммитить всё подряд).
    - Состояние задач = Postgres planner (через API), НЕ в репозиториях проектов.
